# ADR-0014: The adapter contract — a generic model in the app, the engine in the adapter (db, storage, code host)

**Status:** Accepted
**Date:** 2026-08-16
**Deciders:** Alwurts

## Context

`ServeAdapter` ([`../../framework/toolchain/src/adapter.ts`](../../framework/toolchain/src/adapter.ts))
names `db`, `storage` and `secrets` bindings, but the types behind them
are markers only. Three questions came due at once (owner session,
2026-08-16):

- The ERP starter is about to need file storage (PDFs, spreadsheets),
  and the adapter has no storage contract.
- Migrations are generated by our own diff/DDL
  (`factory/host/src/schema/schema-ddl.ts`) and our own snapshot format,
  because `drizzle-kit generate` is a Node CLI and the develop plane has
  no shell. That is the wrong reason to own a migration engine.
- Portability ([ADR-0006](0006-base-runtime-is-platform-resolved.md),
  [ADR-0011](0011-eject-rule.md)) and a future second serve adapter both
  need the app-facing surfaces to be nameable, and the framework must not
  care where an app's repository lives (like any ordinary framework).

The alternatives were real: expose the platform bindings directly (D1,
R2) and let other adapters emulate them; or expose vendor protocols
(S3) through an SDK; or define small generic surfaces and let adapters
supply the engine.

## Decision

**One rule for all three:** the app sees a generic model; the adapter
chooses the engine; the framework never chooses an engine or a host.

### Database — the contract is Drizzle's SQLite dialect

- The runtime hands the app a Drizzle SQLite `db` (async result mode)
  and the schema helpers from `drizzle-orm/sqlite-core`. The app never
  sees a driver or a binding. Raw SQL is available only through Drizzle
  (`db.run(sql\`…\`)`).
- The adapter picks the engine: on the host, per-app Durable Object
  SQLite; standalone / eject on Cloudflare, D1 via wrangler; a Node
  adapter may use `better-sqlite3` or libsql. Swapping engines is an
  adapter change, never an app change.
- **Capability floor** (because the engines differ): `db.batch` yes;
  interactive `db.transaction` **no** — D1 stays a supported engine, so
  the floor is D1's. The check unit flags `db.transaction(` as
  unsupported with an agent-grade diagnostic. The floor may be raised
  later, never lowered.
- **Feature set is the stated intersection**: JSON1 yes, `RETURNING`
  yes, FTS5 not promised.
- **Drizzle generates migrations; the framework only applies and
  gates.** `db:generate` becomes a call into drizzle-kit's API (where it
  runs — host, check worker — is decided by the 2026-08-16 probe); the
  `migrations/` directory, journal and snapshots use drizzle-kit's own
  format so a laptop `drizzle-kit generate` on the same tree is
  byte-compatible. What stays ours: the immutable applied ledger
  ([ADR-0005](0005-app-loop-mimics-an-ordinary-repo.md)), the
  destructive-change safety gate, and the CD schema gate. Our own diff /
  DDL / snapshot code is deleted when the replacement lands.
- `db` is always on: a lite app is full-stack by definition (the
  manifest carries `schema` and `migrations`).

### Storage — a small object-store interface with S3 semantics, no S3 protocol

- Opt-in: `manifest.capabilities: ["storage"]`. The host binds it only
  when declared; eject provisions exactly what is declared.
- The app sees a neutral `storage` object with S3-compatible
  *semantics* and nothing vendor-specific: `put(key, body, {contentType,
  metadata})`, `get(key) → {body, size, etag, contentType, metadata} |
  null`, `head(key)`, `delete(key | key[])`, `list({prefix, cursor,
  limit}) → {objects, cursor, truncated}`; bodies are streams. This is
  clause (b) of ADR-0011: framework source small enough to copy into an
  ejected app.
- The adapter supplies the engine: Cloudflare → the R2 binding (thin
  wrapper; the host adds a per-app × per-generation key prefix); Node /
  other → S3 or S3-compatible stores through a small signer inside the
  adapter, or local disk. **No SDK and no protocol in the app.**
- Previews (`pr:N`) start empty, as the database does. Copy-on-write is
  an adapter feature for later.
- **Not in v1:** presigned / direct-to-bucket URLs — uploads and
  downloads go through the app's own routes. Quota and maximum object
  size are host policy, not part of the interface.
- If a widely known package (e.g. Flystorage) is later preferred as the
  surface, it must first be measured against the check-heap and bundle
  budgets like any runtime addition; the default is our own interface.

### Code host — the framework never sees a repository

- Verbs take a file tree; the manifest says nothing about origins; an
  app is a git repository. Where that repository lives is a **harness
  adapter** (`CodeHost` in `factory/host/src/code-host/code-host.ts`):
  Cloudflare Artifacts is the git remote; GitHub would be another
  implementation of the same interface.
- Named, not solved: the harness's own pull-request model and its minted
  agent credentials are the first things a GitHub-backed code host would
  have to map or replace.

## Consequences

### Positive

- The app's vocabulary is engine-free (Drizzle, a five-verb store, git),
  which is what agents and developers already know and what
  [ADR-0011](0011-eject-rule.md) needs.
- A second serve adapter has a definition to implement; eject has a
  list of what to provision (`db` + declared capabilities).
- One migration engine (Drizzle's), one on-disk format, laptop and host
  interchangeable.

### Negative

- The capability floor is D1's: no interactive transactions until the
  floor is raised.
- Storage without presigned URLs streams through the app; large files
  cost app CPU.
- Storage semantics are ours to keep stable.

### Mitigations

- The check unit enforces the floor (`db.transaction(`), so an app
  learns at check time, not in production.
- The interface is tiny and copyable; raising the floor or adding
  presign later is additive.

Implemented by PR 15 (db shim, floor diagnostic, storage).
Implemented by PR 18 (schema gate in verbs; app Env never names the engine).
